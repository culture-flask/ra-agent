# 分词正则改动后的超参数重测报告（第五轮，2026-08-20）

> 背景：用户把 BM25 英文词块正则 `_WORD_RE` 加上了 `-` 和 `_`（让 `CPDI-ND`、
> `related-key` 这类复合词不再被拆开）。本轮回答回一个问题：
> **这个分词改动是否影响第四轮选出的最优超参数（b=0.45 / depth=15 / df=0.03）？**

---

## 0. 一句话结论

**最优超参数没有受到影响。** 在新分词下重跑 576 配置网格，冠军配置与第四轮完全相同
（b=0.45、depth=15、df=3%）；超参数相对旧参数的增益幅度也与第四轮基本一致
（MRR +0.043 / R@10 +0.058，第四轮为 +0.054 / +0.065）。**代码无需再改任何数值。**

但本轮发现并处理了一件更重要的事：**你改的正则原本不生效**--`tokenize()` 用的是
函数内的另一份内联正则，`_WORD_RE` 是个从未被引用的死变量。已修复（见 §1），
修复后的分词改动对检索效果总体近乎中性（§3）。

## 1. 先说清楚：正则改动为什么原本无效，怎么修的

改动前的代码结构：

```python
_WORD_RE = re.compile(r"[a-zA-Z0-9_\-]+")   # 你改了这里

def tokenize(text):
    for seg in re.findall(r"[\u4e00-\u9fff...]+|[a-zA-Z0-9]+", ...):  # 实际用的是这行内联正则
```

实测证据：`tokenize("CPDI-ND related-key")` 改动前后都返回 `['cpdi', 'nd', 'related', 'key']`--
`-` 处照样被切开，`_WORD_RE` 无人引用。

修复：新增 `_SEG_RE = re.compile(f"{_CJK_RE.pattern}|{_WORD_RE.pattern}")`，
`tokenize()` 改用 `_SEG_RE.findall(...)`。现在分词正则只有一处事实来源
（`_WORD_RE`），以后再改字符类不会再"改了不生效"。修复后：

```python
tokenize("CPDI-ND related-key")  -> ['cpdi-nd', 'related-key']
tokenize("Speck32/64 speck32_64") -> ['speck32', '64', 'speck32_64']   # 斜杠仍切分
```

新增单元测试 `test_tokenize_keeps_hyphen_underscore` 锁定该行为。

## 4. 分词改动到底影响了什么（机制分析）

26 个查询里有 6 个 token 集合发生变化（都是含连字符复合词的英文查询）：
`CPDI-ND`、`Rotational-XOR`、`GIFT-128`、`Round-Reduced/Speck32`、`related-key` 等。
新语料中含 `-`/`_` 的复合 token 共 5987 种，占总词频 2.82%。

但逐查询对比后发现，**最终检索结果只有 1 个查询变化**：
"Gimli differential distinguishers"（MRR −0.75，R@10 +0.33）。

两个方向的作用在大部分查询上互相抵消了：

1. **查询侧收益**：`CPDI-ND` 整词匹配 `cpdi-nd`（df=21，唯一命中该文档），
   比 `cpdi`+`nd` 两个碎词更精准；`rotational-xor`（df=44）同理。
2. **语料侧代价**：文档里的 `differential-based`、`deep-learning` 这类连字符复合词
   现在成整块 token，不再贡献 `differential`、`learning` 等单词的词频--
   查询里没连字符的普通词对这些文档的 BM25 分数下降（Gimli 用例正是如此）。
3. **与 df 过滤的交互**：复合词把词频集中到了一起，`related-key` 的 df=263
   超过了 3% 阈值（新库 7308 × 3% = 219），会被查询词过滤规则剔除。
   网格实验显示阈值 3% 依然最优（2% 结果相同，5%/1% 都更差），无需调整。

**使用建议**（写给日常检索）：查带连字符的术语时，查询里也带连字符
（查 "CPDI-ND" 而不是 "CPDI ND"）才能吃到整词精确匹配的红利；
反过来，复合词现在只有带连字符的写法能命中，不带连字符的写法匹配不到它。
